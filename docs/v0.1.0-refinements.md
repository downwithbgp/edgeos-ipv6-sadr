# v0.1.0 normative refinements

**Status:** normative for the v0.1.0 implementation. This document supersedes conflicting text in
`requirements.md`, `security-invariants.md`, `testing-strategy.md`, `operations.md`,
`platform-compatibility.md`, `architecture/ADR-0001-routing-model.md` and `AGENTS.md`.

## 1. Internal classification

* Connected routes are mirrored only for interfaces explicitly listed in `internal-interface`.
  Unknown interfaces are not trusted.
* A policy interface, a next-hop covering interface, and any bridge/VLAN ancestor or child of one is
  excluded from auto-whitelisting. Declaring one as `internal-interface` is a configuration error.
  The exclusion is re-evaluated on every reconcile, not only at commit time.
* `destination-exception` is exact. Its exact main-table route is mirrored; more-specific routes are
  not. A route on a policy interface, an ECMP/ambiguous exact route, or a gateway without a covering
  internal/connected route is rejected or guard-only.
* Withdrawal of an internal route leaves the per-prefix guard and reports `protected`/`incomplete`.
  Intentional removal of the exception removes the real route before the guard, then removes the
  guard and the provider-table internal guard.

## 2. RPDB guards

* Priority slots: pair A `0/1`, pair B `2/3`, terminal source guard `6`, reserved `7`, range
  `20000–21031`.
* The terminal `from S unreachable` guard is permanent, installed before the source is constrained.
* Every provider table also carries `unreachable <internal-prefix>` guards at a higher metric than
  the provider default. If the internal rule/table is missing while the provider rule survives, an
  internal destination is blocked rather than sent to the provider.
* Active/staging: one pair is active, the other staging. Install/verify the new table and guards,
  install the staging pair, structural/ownership/table check, remove the old pair. If staging is
  before old it takes effect after the new table is verified; if after, old remains until removal.
  The old pair is a previous-effective fallback; terminal and provider internal guards cover missing
  tables. Both pair orders are tested. Post-cutover route lookup verifies the selected table;
  packet-path evidence is generic-Linux/hardware.
* Disabled creation installs no provider route. Disable keeps the internal/provider rules and
  terminal guard but withdraws the provider route. A disabled policy stays disabled across
  recreation. Delete removes the provider route, then pairs, then terminal guard last. Removing a
  source prefix installs the new guard first and removes the old guard last. Deleting a nested /64
  falls to the enclosing policy if one exists (not native routing); test/document.
* The terminal/provider internal guards do not protect against arbitrary privileged deletion of all
  rules/tables or malicious foreign state.

## 3. Desired state and reconciliation

* Commit action: working configuration via `listNodes`/`returnValue`; API diagnostics are hard
  failures.
* Monitor: active configuration via `listActiveNodes`/`returnActiveValue` outside a commit; verified
  read-only on the target. It runs `After=vyatta-router.service`. A failed commit does not change
  active config.
* Boot guard: parses `/config/config.boot` directly for `protocols ipv6-sadr` source prefixes before
  `vyatta-router.service`, writes exact `/run/edgeos-ipv6-sadr/boot-guards.json` intent, then installs
  terminal guards. No persistent snapshot is required.
* Runtime state is `/run/edgeos-ipv6-sadr/{manifest,journal,status,boot-guards,lock}` via systemd
  `RuntimeDirectory`. Kernel state clears at reboot; config.boot is the boot source.
* Observed state: route/rule text; `ip -j -d link` for link attributes only. Treat `FIB table does
  not exist` as an absent managed table.
* Lock, re-read, plan, verify ownership, journal, apply, verify, manifest/status, remove journal.
  No blind replay. Re-check the config generation before apply. Three bounded post-apply
  verifications with short backoff; not polling.
* Boot-guard intent records exact tuples. An orphaned guard is removable only when it matches the
  recorded tuple and the source is absent from desired state; otherwise report and refuse.

## 4. Health

* Separate intent, realization, effectiveness and reachability.
* States: `effective`, `incomplete`, `dependency-unavailable`, `protected`, `shadowed`, `conflict`,
  `orphaned-guard`, `failed`, `disabled`.
* Per policy, `disabled` overrides `protected`. Overall severity:
  `failed` > `conflict` > `orphaned-guard` > `shadowed` > `dependency-unavailable` > `protected` >
  `incomplete` > `effective`. `disabled` only when all policies are disabled; mixed disabled/effective
  is `effective`.
* Exit codes: 0 effective, 2 incomplete, 3 dependency, 4 protected, 5 shadowed, 6 conflict, 7 failed,
  8 disabled, 9 orphaned-guard. Human and `--json` output.
* Reachability is `unverified` by default; `next-hop-unresolved` only from neighbour state. A route
  is not proof of provider transit.

## 5. Package and tests

* `prerm remove` refuses when saved or active configuration contains `protocols ipv6-sadr` policies
  or when extension-owned rules/tables remain. `upgrade` is allowed.
* Packaging lands before the installed-package netns run.
* Tests include disabled creation, both pair orders, prefix shrink, nested deletion, exception
  removal, internal-interface ancestor/child exclusion, provider lookup present/internal lookup
  missing, table disappearance, missing terminal default, process kill at each mutation,
  commit-confirm simulation, shadow overlap/from-all/non-source, orphan repair and foreign
  preservation.
* Hardware execution and migration of the manual table/rules are post-v0.1.0; this phase produces
  plans only.

## 6. Source selection

Forwarded, explicitly source-bound local and unbound router-originated traffic are distinct. The
implementation does not modify `gai.conf`, labels, RAs or DHCPv6. Target source-selection tests and
RFC 6724/8043/8028/8678 analysis are qualification deliverables; no automatic optimal-source claim.
